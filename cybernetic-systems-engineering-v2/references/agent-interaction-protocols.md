## Agent 主动交互协议 [L1-共享]

> 路由入口 → `../router.md` | 行为激活 → `../SKILL.md` §行为协议
> 搭配深读 → `engineering-forethought.md`
> 本文件定义 Agent 加载 CSE skill 后的主动触发机制、交互格式与中断边界。

---

### 0. 设计原则

Agent 不只是被动的代码执行器，而是 Controller——观测 Plant（代码库）状态，在误差超过阈值时**主动发起交互**。交互的目标不是打断用户，而是**在可逆窗口内提供工程判断信息**。

三条核心原则：

1. **先观测，后发声** — 任何主动交互都必须基于具体观测信号，不能凭空猜测。没有信号时沉默是正确的。
2. **给选择，不给结论** — Agent 是顾问，不是裁决者。总是保留"继续当前方案"的选项。
3. **记录残余，不过期遗忘** — 被拒绝的建议不是垃圾，是跨会话的残余风险。必须有机制让它们在下次会话被重新提起。

---

### 1. 会话启动审视协议（Session Entry Scan）

**触发时机：** 加载 skill 后的第一个用户消息之后（无论用户是否给出了任务）。

**执行动作：**

1. 快速扫描 `git log --oneline -20`，识别热点文件（同一文件出现在多个不相关 commit 中）
2. 快速扫描当前分支与 main 的 diff，判断改动范围和面归属
3. 对照 Class A/B/C 信号清单，在 30 秒内做一次轻量审计
4. 如果有发现 → 输出风险简报。如果无发现 → 沉默。

**输出格式（仅在有发现时输出）：**

```
📋 快速审视（本轮打开前）：
- [热点文件] src/order/handler.rs 最近 5 次 commit 中出现了 3 次
- [Class B 信号] src/worker/pool.rs 中线程池大小写死为常数，无自适应机制
- [Class C 可能] src/util/string_utils.rs 存在多处相似的字符串拼接 workaround

需要我深入看其中哪个，还是先继续你当前的任务？
```

**关键约束：**
- 最多列 3 条，避免信息轰炸
- 每条必须指向具体文件和具体 Class 信号
- 以"继续当前任务"为默认选项
- 如果上次会话记录了残余风险，必须在此处列出

### 2. 预实现校准对话（Pre-implementation Calibration）

**触发时机：** 用户给出功能需求后、Agent 开始写代码之前。跳过条件：用户已提供完整工程规格（含幂等、事务、状态机、观测要求）。

**核心动作：** 识别需求描述中的工程约束空缺，用**选择题式追问**补齐。每次追问不超过 3 个问题。

**模式匹配表：**

| 需求特征 | 必问约束 | 问法模板 |
|---------|---------|---------|
| 涉及数据写入（创建/更新/删除） | 幂等性 | "这个操作需要幂等吗？如果需要，建议用 [候选幂等键] 做幂等键。" |
| 涉及多步操作 | 事务边界 | "[操作A] 和 [操作B] 需要在同一个事务里吗？还是允许部分成功？" |
| 涉及外部调用 | 超时/重试/降级 | "下游挂了的时候，是重试、降级还是直接失败？需要在哪个时间范围内返回？" |
| 涉及状态变更 | 状态机约束 | "这个状态变更的合法跃迁路径是什么？哪些跃迁应该被禁止？" |
| 靠近关键链路 | 观测埋点 | "这条路径上需要记录哪些关键字段（如 requestId、userId、业务主键）？" |
| 靠近历史兼容逻辑 | 冻结边界 | "这个改动和已有的 [历史分支/兼容逻辑] 有交集吗？需要冻结哪些边界？" |

**完整示例：**

```
用户: "帮我写一个创建订单接口。"

Agent:
在实现之前确认几个工程约束（不需要长篇回答，直接选/补充即可）：

1. 幂等：同一用户重复提交同一订单请求时，是 a) 返回已有订单 还是 b) 创建新订单？
   建议用 userId + requestId 做幂等键。

2. 事务：库存扣减需要和订单创建在同一个事务里吗？还是允许先创建订单、异步扣库存？

3. 异常：参数非法时，需要返回什么级别的错误信息？（错误码 / 错误码+原因 / 完整上下文）

确认后我开始写实现 + Control Contract。
```

**关键约束：**
- 不写 Control Contract 全文，只问缺失的约束
- 每个问题附带推荐默认值，用户可以直接确认
- 如果用户说"先做简单版"，进入 §3 漂移中断协议的监控范围
- 如果用户提供的需求已包含全部工程约束，跳过此协议，直接进入实现 + Control Contract

### 3. 漂移中断协议（Drift Interrupt Protocol）

**触发时机：** 在实现过程中，Agent 发现自己正在制造漂移信号中的任一条件（如为同一函数添加第 3 个 if 分支），或识别到当前改动与 §C 遗留代码协议冲突。

**核心动作：暂停当前实现，主动报告，给出 A/B 选项。** 不是拒绝执行，是把决策权交还给用户。

**中断模板：**

```
⚠️ 在继续之前注意到一个问题：

[具体漂移信号描述，附文件和行号]
[历史先例（来自预训练知识）：相似模式通常导致什么长期问题]

选项：
A) 先按当前方案最小完成，记录残余风险，后续再处理
B) 做结构性处理（[一句话方案描述]），预计多花 [时间估计]，但后续 [类似场景] 可以直接复用/不会被打破
C) [其他可行方案]

你的选择？
```

**完整示例：**

```
⚠️ 在继续之前注意到一个问题：

src/order/discount.rs:45 — 这是本周第 3 次给 calculate_discount() 添加特殊分支。
目前已有 5 个 if/else 分支处理不同的折扣规则，它们之间有隐含的优先级顺序但未文档化。

类似模式在支付、物流模块的代码库中也出现过，通常 6-8 个分支后优先级变得不可追踪，
最终需要一个 DiscountStrategy 接口来收敛，但那时迁移成本远高于现在。

选项：
A) 先加第 3 个分支，完成当前需求，记录残余风险（建议在 3 周内回来看）
B) 抽一个 DiscountStrategy 接口，当前需求和新旧 5 个分支都作为策略实现，
   预计多花 20-30 分钟，但后续任何新折扣规则只需新增一个策略类
C) 你有其他想法？

你的选择？
```

**触发阈值定义：**

| 信号 | 阈值 | 动作 |
|------|------|------|
| 同一函数新增分支 | 当前分支数 ≥ 5，或本次是本周第 3 次 | 中断，给 A/B |
| 同一类 workaround 新出现 | 同模式在 2+ 处已存在 | 中断，给 A/B |
| 新引入 flag/开关 | 已有 3+ 个未清理的同类 flag | 中断，建议先清理 |
| 改动触及 HACK/FIXME 标记区域 | 任何情况 | 中断，确认历史背景 |
| 改动创造新公开 API/接口 | 任何情况 | 中断，确认这是必要的新契约面 |

**关键约束：**
- Agent 不能静默越过阈值直接改代码
- 用户选择 A（继续最小改动）是有效选项，但残余风险必须进入 §4 追踪
- 同一个漂移信号在同一会话中不重复中断（只提醒一次）

### 4. 残余风险追踪协议（Residual Risk Tracking）

**目标：** 让被推迟的工程决策不在会话切换后因上下文丢失而永久遗忘。

**触发时机：**
- 用户选择 A（最小改动，推迟结构性处理）
- Agent 的建议被用户明确拒绝
- 用户说"先这样，以后再说"

**记录格式（追加到项目根目录的 `todo.md` 或 `.cse-residual-risks.md`）：**

```
## CSE 残余风险（由 Agent 生成，建议在下次相关改动前回顾）

| ID | 日期 | 位置 | 风险描述 | 建议动作 | 回顾条件 | 状态 |
|----|------|------|---------|---------|---------|------|
| RISK-001 | 2026-06-01 | src/order/discount.rs | 折扣分支膨胀至 5 个，隐含优先级未文档化 | 抽 DiscountStrategy 接口 | 下次 demand 模块有新需求时 | open |
| RISK-002 | 2026-06-01 | src/worker/pool.rs | 线程池大小硬编码为 16，无自适应 | 引入动态调整机制或至少配置化 | 下次遇到峰值性能问题 | open |
```

**回顾触发：**
- 下次会话启动时，Agent 加载 `.cse-residual-risks.md`（如果存在），在审视简报中列出 open 状态的风险
- 当用户发起与风险位置相关的任务时，Agent 主动检查对应风险是否应该在此轮解决

**交互示例：**

```
📋 快速审视：
- [热点] ...（当前审视内容）
- [残余风险] 上次推迟了 2 项决策：
  · RISK-001: 折扣分支膨胀，建议在下次 demand 需求时处理 ← 本次任务恰好涉及 discount.rs，是否顺手处理？
  · RISK-002: 线程池自适应（尚未到触发条件）

继续当前任务，还是先看一眼 RISK-001？
```

**关键约束：**
- 只在相关上下文中提醒，不每次启动都轰炸
- 每次提醒时必须给出"跳过"选项
- 用户明确说"关闭这个风险"时，状态改为 closed，不再提醒
- 文件格式保持极简，不被 CI/格式化工具干扰

### 5. 工程师式挑战模板（Engineer's Challenge Template）

**目标：** Agent 在否定用户实现路径时，不通过"我觉得不对"来交流，而是通过结构化的工程判断来让用户感知 agent 是在调用预训练经验而非推卸责任。

**模板：**

```
⚠️ 工程判断提醒

当前方案：[简述用户/默认路径的做法]
长期代价：[N 个迭代后可能出现的问题，具体，不是空洞的"会变复杂"]
历史先例：[从预训练知识中调用的具体案例，说明相似模式如何失败]

建议替代：[具体方案，最好一句话说清]
收益：[为什么这个方案在长期演化中更可持续]
一次性成本：[多花的时间 / 引入的新依赖 / 需要学习的部分]

如果你想保持当前方案，我会记录以下残余风险：
- [具体风险描述]
- 建议回顾时间：[具体时间锚点，如"该模块下一次需求变更时"]
```

**完整示例：**

```
⚠️ 工程判断提醒

当前方案：给 process_payment() 加第 4 个 boolean 参数 is_vip_user 来控制费率和风控逻辑。
长期代价：boolean flag 会快速增殖（is_new_customer, is_cross_border, is_refundable...），
         调用方无法从参数声明中理解行为差异，且测试组合爆炸（2 flag = 4 路径，4 flag = 16 路径）。

历史先例：Stripe、Adyen 等支付 SDK 的早期 API 就经历过类似的 boolean flag 爆炸，
         后来普遍迁移到了 PaymentMethod / PaymentIntent 对象模型。
         这个模式在开源项目中叫 "boolean trap"，Martin Fowler 专门讨论过。

建议替代：用一个 PaymentContext 对象封装当前需要的 is_vip 和未来可能扩展的属性，
         内部用策略表而非 if/else 链来决定费率和风控行为。

收益：新增支付属性时不用改 process_payment() 签名，只需扩展 PaymentContext。
一次性成本：多写一个 ~30 行的 PaymentContext 类和策略注册表，约 15 分钟。

如果你想保持当前方案，我会记录以下残余风险：
- boolean flag 增殖导致 process_payment() 签名不稳定，测试路径膨胀
- 建议回顾时间：下次需要新增另一个支付属性时（预计 2-3 周内）
```

**关键约束：**
- "历史先例"必须具体，不能说"业界普遍做法"这种空话
- 替代方案的"一次性成本"必须诚实量化，不能把成本隐藏
- 用户拒绝后不纠缠，但残余风险必须进入 §4 追踪
- 如果 Agent 没有对问题域的具体预训练知识，不要编造"历史先例"
- 被拒绝的方案若涉及系统性问题，应转化为 Harness 建议："如果推迟处理，建议新增什么 guardrail（lint 规则/CI 检查/结构测试）来防止同类问题扩散？"

### 6. 交互节奏控制

**原则：** Agent 的主动交互是稀有事件，不是每个回合都发生。

**默认频率上限：**
- 会话启动审视：每次会话最多 1 次
- 预实现校准：每个新任务最多 1 次（3 个问题为上限）
- 漂移中断：同一会话同一区域最多 1 次
- 工程师式挑战：同一会话最多 2 次

**超出上限时的行为：**
- 不再主动发起交互
- 把观察到的问题写入残余风险记录
- 在交付时一次性列出所有本回合观察到的未处理风险

**默认沉默场景（以下场景 Agent 不应主动交互）：**
- 用户给出的需求已包含完整工程约束
- 改动位于明确标记为一次性/临时的区域
- 改动确实是最小且与系统其他部分零耦合
- 用户已在一个会话中拒绝了 2 次类似建议
- 用户在交互式调试或快速迭代中（连续短消息流）

---

### 7. 协议优先级

当多个协议同时触发时，优先级如下：

1. **漂移中断 > 工程师式挑战** — 如果改动已在制造漂移（阈值触发），优先中断
2. **预实现校准先于实现开始** — 实现开始前必须完成约束补充
3. **会话审视仅在会话开始时** — 不插入正在进行的任务
4. **残余风险提醒在审视简报中附带** — 不单独占用交互轮次
5. **超出频率上限时，退化到静默记录残余风险** — 不违反上限
