### 0. 审查哲学

SWE-CI 论文的量化结论：在长程代码维护中，**大多数模型的零回归率低于 0.25**——即使模型在单次修复上表现很好，一旦进入连续迭代，回归会变成主要失败模式。因此审查的核心目标不是"找出所有问题"，而是**降低未来回归的概率**。

四条原则：

1. **回归是第一公民** — 旧行为是否被破坏是审查时首先要回答的问题，排在代码风格和抽象质量之前
2. **证据驱动** — 每条发现必须绑定证据来源（命令输出/测试报告/文件路径/行号）+ 置信度标注（High/Medium/Low），不放空枪
3. **审查的产出是 guardrails** — 每次审查不只是挑毛病，更要把发现的系统性问题转化为可执行的防护规则（lint 规则、结构测试、CI 检查），让下一次 agent 或人更不容易再犯
4. **审查深度与风险成正比** — 高风险区域（认证/授权/支付/账务/数据迁移/并发/缓存/跨服务协议/序列化/加密）默认深读，低风险区域默认浅读

---

### 1. 审查模式

从以下四种模式中按优先级自动匹配，或由用户显式指定：

| 模式 | 触发条件 | 审查对象 |
|------|---------|---------|
| **DIFF_REVIEW** | 存在未提交 diff / PR / 分支差异 | 当前变更集（diff） |
| **COMMIT_REVIEW** | 用户指定了某次 commit | 单次提交的完整变更 |
| **COMMIT_RANGE_CROSS_REVIEW** | 用户指定了 commit range（如 `HEAD~10..HEAD`） | 多轮演进的累积效应、回归高发点 |
| **FULL_CODEBASE_AUDIT** | 用户要求全库审计，或范围过大无法缩减 | 高风险区域 + 近期活跃区域 + 低测试覆盖区域 |

默认推断优先级：有 diff → DIFF_REVIEW；有单一 commit → COMMIT_REVIEW；有 range → COMMIT_RANGE_CROSS_REVIEW；否则 FULL_CODEBASE_AUDIT。

---

### 2. 审查前置：建立基线

在输出任何审查结论之前，先在不修改代码的前提下运行基线：

1. **静态检查** — lint / typecheck / format check（至少一项）
2. **快速测试** — 最便宜的测试子集（如单元测试），记录：通过数/失败数/耗时
3. **如果可行** — 运行全量测试套件或最能代表关键路径的子集
4. **记录 flaky 迹象** — 同一测试偶发失败，标注为 flaky 而非直接下结论

基线不通过 → 审查结论中必须区分"基线已存在的失败"和"本次改动引入的失败"。

---

### 3. 回归优先检查清单

以下 5 项覆盖所有审查模式，按优先级排列：

1. **旧行为是否被破坏** — 对比接口契约、错误语义、默认值、边界条件前后的变化。重点关注：公共 API 返回值类型/结构、异常类型、状态码、副作用顺序
2. **是否引入脆弱特判或硬编码** — 识别"未来一个需求过来就会崩"的模式：硬编码常量、隐式优先级、特殊分支无文档、flag 参数无生命周期管理
3. **是否破坏模块边界或引入隐式耦合** — 检查：是否跨越了冻结边界、是否新增了共享接口或共享状态、是否在调用方引入了对实现细节的依赖
4. **是否新增/更新了足够的测试来锁住行为边界** — 检查：修改的方法是否有对应的测试、边界条件是否被覆盖、错误路径是否有断言、是否存在只测 happy path 的测试缺口
5. **改动在 N 个迭代后的可维护性** — SWE-CI 的 future-weighted 视角：如果这个改动被维护 3 个迭代后，会变得更清晰还是更混乱？是收敛了复杂度还是掩盖了复杂度？

---

### 4. 审查输出分级

每条发现按以下 5 级分类输出：

| 级别 | 定义 | 典型触发 |
|------|------|---------|
| **Must-fix** | 阻塞合并 | 安全漏洞、数据损坏风险、明确破坏旧行为且无兼容路径、零回归违约 |
| **Should-fix** | 建议合并前修 | 脆弱特判、边界模糊、测试缺口、隐式耦合、关键路径缺日志 |
| **Follow-ups** | 可转为后续任务 | 技术债清理、文档补全、重构建议、性能优化 |
| **Tests to add** | 要求新增的测试 | 具体到测试文件/测试函数名/断言对象/边界条件 |
| **Risk Register** | 风险登记 | 影响面 × 发生概率 × 可探测性，附带建议回顾时间锚点 |

每条发现的标准格式：

```
- [级别] 文件:行号 — 发现描述
  证据：[命令输出/测试结果/代码引用]
  置信度：[High/Medium/Low] — [理由：如"基于静态分析，未经过运行时验证"]
  建议：[最小修复方案或替代设计]
  Harness：[建议新增的 guardrail，如 lint 规则/结构测试/CI 检查]
```

### 5. Harness Backlog 生成

每次审查结束后，把发现的**系统性问题**转化为可执行的防护规则。这是审查最持久的产出——代码会变，但 guardrails 会持续阻止同类问题。

**转化模板：**

| 发现 | 为什么是系统性的 | Harness 建议 |
|------|----------------|-------------|
| [具体发现] | [为什么不会只发生这一次] | [lint 规则 / 结构测试 / CI 检查 / 危险 API 禁用 / 契约测试类别] |

**典型示例：**

| 发现 | 系统性原因 | Harness 建议 |
|------|-----------|-------------|
| 多处 SQL 使用字符串拼接 | 团队未统一查询构建方式 | 引入 lint 规则禁止 `"SELECT.*"+` 模式，强制使用参数化查询 |
| 公共 API 返回值类型被修改 | 接口缺少契约测试 | 新增契约测试锁住返回结构和字段类型 |
| 重试逻辑散落在 3 个服务中各自实现 | 缺少统一的重试机制 | 抽取公共重试模块 + 结构测试确保所有 RPC 调用通过统一入口 |
| feature flag 已积累 5 个且无清理计划 | flag 的生命周期未被管理 | CI 检查：每个 flag 必须有过期日期，过期后 CI 失败 |

### 6. 演进叙事审计（COMMIT_RANGE_CROSS_REVIEW 专有）

这是唯一需要读取多轮 git 历史的审查模式，借鉴 SWE-CI 的长期演进视角。

**步骤：**

1. **提取提交列表** — `git log --oneline <range>`，按时间排序
2. **构建演进叙事** — 为每个关键提交标注：
   - 解决了什么问题（意图）
   - 引入了什么新约束（新接口/新状态/新配置/新依赖）
   - 是否埋下长期维护成本（特判、workaround、隐式契约）
3. **识别回归高发点** — 在 range 内被修改 3+ 次的公共模块/共享接口/底层工具
4. **定点对比关键提交** — 选取 range 的头部和尾部，对比：接口契约、错误语义、默认值、边界条件、性能特征
5. **输出未来加权建议** — 哪些地方需要重构（因为漂移已经发生）、哪些地方必须补测试/补约束/补文档以防止同类错误反复出现

**输出格式（在常规审查输出之外追加）：**

```
## 演进叙事
- [起始提交] → [结束提交]，共 N 次提交，跨度 D 天
- 主要演化方向：[一句话总结这个 range 内系统发生了什么变化]

## 回归高发点
- [文件/模块路径] — 在 range 内被修改 M 次，涉及 [耦合模块列表]
  · 风险：[耦合放大的具体路径]
  · 建议：[冻结建议或重构方向]

## 未来加权建议
1. [结构性重构]: [理由 — 不重构未来 X 个月会怎么样]
2. [测试补强]: [具体缺口]
3. [Harness 改进]: [新增什么 guardrail]
```

### 7. 高风险区域清单

以下区域在任何审查模式下都应视为高优先级深读目标：

- 认证与授权（authentication / authorization）
- 支付与账务（payment / billing / accounting）
- 数据迁移与 schema 变更（migration / schema）
- 并发与缓存（concurrency / cache / distributed lock）
- 跨服务协议（API / 事件 / 队列消息格式）
- 序列化与反序列化（serialization / deserialization）
- 加密与密钥管理（crypto / key management）
- 资源生命周期（connection pool / file handle / worker lifecycle）

对于这些区域，默认要求：信任度不低于 Medium，不允许 Low 置信度的结论直接作为 Must-fix 依据。

---

### 8. 停止条件

- 如果发现高危安全漏洞或数据损坏风险：**立即停止后续审查**，先输出阻断性告警 + 最小复现 + 建议隔离/回滚策略
- 如果测试/构建环境无法运行：输出"无法运行的根因树 + 下一步获取证据计划"，不要臆测结论
- 如果基线不通过且无法区分新旧失败：标注此不确定度为 Low 置信度，不据此下 Must-fix 结论
