## §C: 遗留代码安全变更协议

> 本协议自包含，不依赖其他章节即可执行。
> 概念关系见 `../references/knowledge-graph.md` §支线C。
> 决策准则深度展开 → `decision-principles.md`

---

### 1. 问题信号

以下任一信号出现，优先按本协议处理：

- AI 顺手重命名变量、方法、枚举
- 抽取公共方法时改动了调用链
- 合并"看起来一样"的分支逻辑
- 删除"重复"代码时清除了隐含的业务规则
- 改动历史兼容逻辑（标记了 `// HACK` 或 `// FIXME` 但未理解其背景）
- 把旧数据迁移路径当成冗余代码删除
- 不评估共变关系就做抽象

**遗留代码的特性：** 很多"不优雅"的代码是历史 bugfix、客户特例、数据修复逻辑、兼容规则。AI 看不到这些背景。

---

### 2. 边界冻结协议：只扩展，不改写

在遗留代码上，默认策略是只扩展不改写。

**冻结清单模板（可直接复制使用）：**

```
本次变更冻结边界：
1. 禁止修改的文件夹/包: [  ]
2. 禁止修改的文件: [  ]
3. 禁止修改的函数/方法: [  ]
4. 禁止修改的 API 签名: [  ]
5. 禁止修改的数据库字段语义: [  ]
6. 禁止删除的历史分支: [  ]
7. 禁止合并的逻辑路径: [  ]
8. 禁止调整的调用链: [  ]
9. 本次只允许的操作: [ 新增 / 补测试 / 新增扩展点 / 新增配置开关 ]
10. 如果认为必须重构，先说明原因，不直接改。
```

**只扩展不改写的 5 种模式：**

1. **新增 Adapter** — 包装旧逻辑，新调用走 Adapter
2. **新增策略类** — Strategy/Policy 模式注入新行为
3. **新增扩展点** — 在现有流程中预留 hook/回调
4. **新增配置开关** — feature flag 控制新旧路径
5. **新增兼容分支** — 留旧路径，新条件走新路径

---

### 3. 特征测试协议

**定义：** 在改代码之前，先写测试锁住当前行为。不改实现，只描述输入-输出。

**四步法：**

| 步骤 | 动作 | 产物 |
|------|------|------|
| 1. 识别主入口 | 找到要改的函数/模块的公开入口 | 入口函数列表 |
| 2. 记录当前输出 | 正常输入 / 边界输入 / 异常输入 → 当前返回 | 输入-输出对照表 |
| 3. 锁定历史分支 | 已知的特殊分支、兼容数据、历史 bugfix | 特殊 case 的断言 |
| 4. 标注来源 | 每个 case 注明来自线上记录/historical context/现有文档 | 可追溯的测试注释 |

**特征测试示例：**

```
// 特征测试 — 不改实现，锁当前行为
// 来源：订单金额为 0 时，现有逻辑返回 -1（历史上的免费订单处理）
test_order_amount_zero_returns_negative_one() {
    result = process_order(Order{amount: 0})
    assert result == -1  // 锁定旧行为，即使看起来不合理
}
```

**执行规则：**
1. 先补特征测试，再改代码。
2. 特征测试的目标不是"正确"，而是"描述现状"。
3. 改动完成后，特征测试如果失败，先确认是"故意改的行为"还是"误改历史逻辑"。
4. 如果故意改历史行为，必须先获得模块 owner 或总体设计部裁决。

### 4. 抽象审查协议

**核心原则：** 抽象的目标不是减少重复，而是减少错误耦合。

**判定规则：**

1. 两个调用点的发布节奏、故障域或 owner 不同 → 先不要抽象
2. 抽象会扩大共享 API 面、共享状态面或统一门禁面 → 先怀疑这是错误抽象
3. 代码相似但业务语义、失败模式或演化方向不同 → 不应抽象
4. 在决定抽象前，必须回答：它们未来真的会同时变化吗？

**允许 WET（Write Everything Twice）：**

- 如果两段逻辑当前相似但未来不保证一起变化，允许先物理重复
- 宁可保留两份小实现，也不要为了复用把两个生命周期不同的模块绑死
- DRY 没有被废除，但它必须服从模块职责、故障隔离和长期演化

---

### 5. 扩展点策略目录

| 模式 | 适用场景 | 风险 |
|------|---------|------|
| Adapter | 需要包装旧接口而不改其内部 | 多一层间接调用，调试链变长 |
| Strategy/Policy | 需要从多个算法中选择而不改调用方 | 策略爆炸时退化成配置地狱 |
| Feature Flag | 需要灰度或可回退地切换行为 | 长期残留变成死代码 |
| 兼容分支 | 需要同时保留新旧两条执行路径 | 分支过多的认知负荷 |
| Extension Hook | 需要在固定流程中插入新步骤 | 不约束 hook 执行顺序会导致非确定性 |

**选择原则：**
1. 优先选可逆的（Feature Flag > 兼容分支 > Adapter）
2. 每个扩展点显式声明：谁安装它、谁移除它、什么时候移除
3. 不允许扩展点变成"以后再说"的万能入口

---

### 6. 反模式

| 反模式 | 说明 |
|--------|------|
| 顺手重构 | 在业务需求交付路径上同时做结构性重构 |
| 以优雅之名删业务补丁 | 把隐含业务规则当成"坏味道"清理 |
| 合并非共变分支 | 把发布节奏、owner、故障域不同的两段逻辑强行抽象 |
| 改历史兼容逻辑 | 改动标注了历史背景的分支、常量、特殊条件 |
| 不补特征测试就改 | 不锁旧行为直接修改，上线后才发现倒退 |
| 扩展点无生命周期管理 | 加了 flag / hook / adapter 但不说何时移除 |

(完整决策准则见 `decision-principles.md` §抽象审查)
