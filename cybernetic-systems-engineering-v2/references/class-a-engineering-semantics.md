## §A: 工程语义闭环协议

> 本协议自包含，不依赖其他章节即可执行。
> 概念关系见 `../references/knowledge-graph.md` §支线A。
> 理论基础深读 → `gda-framework.md`

---

### 1. 问题信号

以下任一信号出现，优先按本协议处理：

- 事务边界模糊 — 多步写入没有显式事务包裹
- 幂等性缺失 — 同一请求重复发送会产生副作用
- 参数校验不足 — 非法输入穿透到核心逻辑
- 异常吞没 — 真异常被 `catch` 后只返回模糊失败，丢失根因
- 关键日志缺失 — requestId、userId、业务主键、失败原因未记录
- 状态转换无约束 — 可以从未定义路径进入非法状态
- 错误处理静默 — 部分成功部分失败却被视为整体成功

---

### 2. Control Contract 实操：从需求描述升级为工程约束

在让 AI 生成代码之前，先写出控制合同。不是写"做什么"，而是写"什么不能违反"。

**反例 — 纯需求描述：**
> 帮我写一个创建订单接口。

**正例 — 工程约束：**

```
实现创建订单接口，要求：
1. 同一 userId + requestId 组合必须幂等（重复请求返回已有结果）。
2. 库存扣减与订单创建必须处于同一事务边界。
3. 参数非法时返回明确错误码与原因，禁止吞异常。
4. 关键路径必须记录 requestId、userId、orderId、失败原因。
5. 禁止修改已有订单状态机枚举值。
6. 先补语义层单测，再实现代码。
```

**合同字段映射：**

| 约束 | 映射到 Control Contract v2 字段 |
|------|-------------------------------|
| 幂等要求 | Primary Setpoint + Guardrail Metrics |
| 事务边界 | Constraints |
| 参数校验 + 异常不吞 | Constraints + Rollback Trigger |
| 日志埋点 | Observability Evidence |
| 禁改状态机 | Boundary |
| 先补单测 | Acceptance + Sampling Plan |

### 3. 验证分层

必须逐层验证，不跳过。

| 层 | 名称 | 检查内容 | 命令示例 |
|----|------|----------|----------|
| L0 | 快回路 | 类型检查、lint、单测子集、边界参数测试 | `cargo check` / `npm run lint` / `pytest -k unit` |
| L1 | 中回路 | 模块集成测试、事务回滚验证、幂等验证、异常路径覆盖 | `cargo test --lib` / 集成测试套件 |
| L2 | 慢回路 | 真实数据库 schema、真实 broker、真实网络、压测、灰度 | 预发布环境 / canary / 影子流量 |

**原则：**
- L0 不稳定，不进入 L1。L1 不稳定，不进入 L2。
- L0+L1 通过 ≠ L2 通过。必须在 L2 级别确认一次。
- 涉及数据库类型转换、PG_CH、真实扩展加载的，必须在 L2 验证。

---

### 4. Review 清单（7 项工程语义检查点）

修改代码后，逐项检查：

1. **重复提交保护** — 存在幂等键且生效
2. **原子性** — 多步具备正确的事务边界
3. **部分失败回滚** — 不存在部分成功部分失败被静默
4. **异常可见** — 根因不被 catch 吞没，不返回模糊错误
5. **可观测性** — requestId + 业务主键 + 失败原因已记录
6. **状态机合法** — 不存在未定义的跃迁路径
7. **失败不降级为成功** — 不把出错状态伪装成正常返回

---

### 5. 反模式

| # | 反模式 | 说明 |
|---|--------|------|
| 1 | 假收敛 | 单测通过，但真实环境条件（schema、网络、并发）未覆盖 |
| 2 | 双真相 | 文档说一套、主链做一套、备用路径又一套 |
| 4 | 弱断言 | 只检查 `is_ok()`，不验证行为语义 |
| 6 | 离线当 gate | 真实 schema / 真实扩展 / 真实网络问题无法由 stub 替代 |

(完整反模式清单见 `quality-gates.md`)

### 6. 端到端示例

**场景：** "本地 cargo test 全绿，但真实 Windows + VPN 环境下回测炸了。"

**按本协议执行：**

1. **信号识别** → 属于工程语义缺失（Class A），L0/L1 通过但 L2 失败
2. **Control Contract** → Primary Setpoint: 恢复真实环境通过；Acceptance: 真实数据库 schema 下回测通过；Constraints: 不改动 schema
3. **验证分层** →
   - L0: 修复后的单测
   - L1: 锁定关键 SQL 与 schema 分支的契约测试
   - L2: 真实 Windows + VPN + 真实数据库环境回测
4. **Review** → 检查是否因 cast 行为、驱动序列化差异或扩展加载顺序导致
5. **交付** → 附带 Recovery Evidence（修复后回测通过的具体环境与命令）+ Observability Evidence（失败日志与成功日志对照）
